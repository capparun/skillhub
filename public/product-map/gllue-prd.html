HUNTER · CUSTOMER OPTIONAL INTEGRATION

Gllue 人才库集成 · 一期 PRD

Gllue 是客户可选的内部人才渠道与 ATS 出口。它以独立插件存在，不写死进 LinkedIn，也不改变未启用客户的主流程。

一期需求已确认 · 待能力审计与真实验收

闭环一：复用库内人才

JD → JBF 确认 → 询问是否搜索 Gllue → 确认人数（默认建议 50） → 完整读取本轮简历并统一评分 → 本地 HTML 审核报告 → 人工决定是否继续外部寻访

闭环二：外部候选人回流

LinkedIn 最终短名单 → 选择需要入库的人选 → Gllue 查重 → 整批预览 → 逐人确认新建或更新 → 找到职位则关联 → 找不到职位不新建，候选人照常入库 → 写后读取核验

分层与独立插件入口

层级负责不负责
Skill搜索人数、批量编排、JBF 评分、人工确认、HTML 报告页面解析和隐式写入

现有命令先审计复用

login · test-connection · search-candidates · get-candidate · check-exists · search-jobs · get-job · add-candidate

候选能力缺口只有在确认无法复用现有命令后才新增：能力预检、字段差异、已有候选人更新、职位关联和 HTML 报告。

关键业务规则

  • Gllue 搜索发生在 JBF 确认后；结果不能静默修改已确认 JBF。
  • 搜索前必须询问人数；50 是建议值，不是固定上限。
  • Gllue 与 LinkedIn 使用同一 JBF 评分标准，但报告中分开呈现来源。
  • 优先使用库内已有且验证过的联系方式；真实触达仍需人工确认。
  • 其他顾问或其他项目正在推进时，默认阻止触达，直到获得协作或转交确认。
  • 查重命中不创建重复记录；先给出字段更新建议。
  • 整批生成预览，真实写入逐人确认；不确定写入不得自动重试。
  • 报告只保存到本地任务目录，不上传敏感信息。

真实验收顺序

  1. 审计现有 8 个命令的原子性、输入输出和真实状态。
  2. 验证连接、登录、租户、搜索入口和单份完整简历读取。
  3. 经用户确认后测试 50 人读取速度、失败率和续跑。
  4. 根据测速决定是否增加每 10 人检查点。
  5. 再开发确有缺口的更新、关联和报告能力。
  6. 最后对明确测试候选人逐项完成真实写入和回读验收。
