# 猎聘寻访 Site Adapter

浏览器业务使用官方 `sites` 入口发现的 liepin Adapter；本地任务使用包内 `tools/liepin-mcp/local.mjs`。不配置独立 hunter-liepin MCP。此包仍为开发候选，安装与真实业务验收分开报告。

## 业务目标与完成标准

目标是帮助用户找到符合岗位要求的人，并在用户明确授权的范围内收藏到指定分组。报告用于解释依据和结果，生成报告不代表寻访完成。先确认本轮覆盖范围和停止条件；没有找到可确认匹配的人时如实说明，不为完成收藏数量降低要求。

搜索前建立“岗位要求→平台筛选→详情核实”对应表。平台可准确表达且不会排除已确认例外的硬条件必须进入每个搜索轮次的 filters，不能仅写在评估说明里。先用 prepare 的 verify_only 回读真实选项；不猜测“本科及以上”“5年以上”等标签或把单个区间当作开放下限。平台无法准确表达的条件保留到详情核实，并说明原因。多关键词轮次共用已核实的筛选基线；可用包内 lib/search-plan.mjs 的 composeKeywordRounds 构造，换词不得丢条件。设置后核对控件和摘要，提交搜索后再核对结果，不能把 prepare 当作已搜索。

搜索前先探索职位别名、核心技术词与容易混入的方向，记录关键词假设；用首轮列表和详情验证，再提出下一轮调整。不得将公开关键词研究写成猎聘命中效果。

逐条复核已读取列表：相关线索明确或信息不足以判断者进入详情队列；只有已明确无关者才跳过并保存职位相关理由。详情数量由核实需要决定，不固定限制为3份，也不机械全读；开发验收配额不能沿用为正式寻访规则。若现有授权或预算不足，保留队列并说明差额，不擅自扩大或宣称整页完成。

人选的技能、经验和资格与岗位逐项对照；关键条件缺证据者记录具体补问，不因列表未写就判定不符合。标准确认后，在用户已明确授权的寻访范围内，按职位相关证据辅助判断值得跟进的人选并收藏，不要求逐人再次审批。收藏表示进入寻访池，不表示满足全部条件或最终录用。关键门槛未证实与明确不满足要分开；边界情况集中展示证据和取舍供用户校准，反馈只更新后续规则，不擅自取消已有收藏。Agent不自行作最终录用判断。

完整业务决策和停止路径见 [目标闭环](references/outcome-workflow.md)。

## 入口选择

- 新寻访：读取 [任务流程](references/workflow.md)，先整理需求、询问本次收藏目标分组列表，再确认试搜计划。
- 继续任务：本地 `task` 的 brief/stats/detail-targets，必要时 show；复用任务，不重建以重置计数。
- 浏览器：先发现官方 liepin Adapter 的实际 schema，再调用 tabs/bind/connect/prepare/search/results/next-page/open-detail/current-detail/detail-batch/saved-search/favorite/favorite-list/favorites。tabs/bind 通过明确的兼容接口发现并认领已打开页面；先 tabs，再以返回 ID 与完整 URL 调 bind。不要直接把普通 js 会话 ID 当作已绑定 Adapter 页面。
- 本地评估与导出：local.mjs 的 task/report，无需浏览器。
- open-detail/detail-batch 需要已验证的同会话标签兼容构建；未安装时应明确报错，不改用隐藏属性。

## 任务数据的持久保存

正式寻访的任务文件、共享账号scope、详情与报告保存在用户指定的持久私有目录，不使用系统临时目录作为唯一副本；临时目录仅用于可丢弃的合成测试或构建。目录应排除Git与安装包分发，不能为保存账本把候选人资料提交到仓库。

继续任务先核对原任务与所绑定scope均存在且可读。交接记录只保存数据路径和脱敏状态，不代替原账本。任务或scope缺失时，先查可靠备份；不能按摘要猜造身份、回执、授权哈希或共享计数，不能新建空任务继续写入。需要改变原任务范围或恢复方案时说明缺失事实，由用户决定；已获授权仍保留，不因恢复数据重复申请同一动作。

## 执行原则

1. 复用用户已授权范围，不为同一操作反复询问。授权记录中的时间、范围、确认人必须来自真实对话；工具能写授权记录不表示 Agent 可以自行扩大范围或预算。
2. 浏览器业务仅通过 opencli-mcp Site Adapter 串行执行，不依赖 Codex CUA、computer use 或宿主界面工具，不在失败时自动切换这些通道。无法通过 Adapter 完成的步骤明确报出缺口，保留状态供用户处理。本地 `doctor` 只检查本地依赖；连接验证、真实页面验证、业务结果验证分别报告。connect 明确打开 Adapter 自己的搜索页；已有绑定则复用，不反复 connect。
3. 设置筛选和提交搜索是不同动作。prepare 不点击搜索，但站点可能自动刷新；search 只执行已批准轮次的搜索及页数。不要在 prepare 后额外用其他通道点击“搜索”。
4. 读多条列表和多份详情，使用稳定观察 ID 和持久队列，不用姓名或列表序号作为跨轮身份。详情保留可见全文、分段、缺口与来源；partial 不写成完整简历，未解锁字段不推断。
5. 页面白屏、登录失效、风险提示或操作结果不明时立即停止本轮。保留已保存结果，通过状态核对恢复；不要刷新/重新搜索碰运气，也不要换 ID 重放未知写操作。
6. 描述用户可见动作，例如“点击第 2 条已核对卡片的姓名”“向下滚动 320 像素”。只读取 DOM 时写“读取…，未点击”；指令返回不等于业务成功，依据回读区分已派发和已确认。
7. 不发消息、不索要附件、不解锁。收藏、取消收藏、方案保存或删除只在相应授权范围执行。不要修改站点检测脚本或声称零风控风险。
8. 评估仅依据职位技能、相关经验、资格与职责，使用 supported/contradicted/unknown 和原文引用。个人敏感属性不用于评估、排序或默认筛选；有疑问保留待核实项，由招聘人员作决定。
9. 仅关闭本会话拥有的标签；用户原有标签保留。进程重启后不能凭旧 tab_id 自动认领关闭权限。

## 交付

正文优先显示：本轮搜索覆盖、已核实人数、已确认收藏的人选与准确分组、主要技术依据，以及尚未完成的关键核实。收藏成功必须有平台回读依据，未执行、失败、结果未知分别列明；已收藏者不重复添加，本地标签不算平台收藏。详细审计与原始简历单独保存。


交付评估结论时，用 report 的 `view:"evaluation"` 生成本地 HTML 摘要报告：先说明证据支持的结论、覆盖范围与缺口，再展示已有评估的重点对照和下一步。完整简历与采集记录放附录，不把全部数据平铺到正文。不把“至少一项条件有证据”写成“整体适岗”，不擅自形成推荐排序。平台工作台用于查看采集过程与全部记录。按需提供 JSON、CSV 或 Markdown。核对唯一候选数、轮次数、详情数、partial 数与短名单阶段；区分初选、深读复评和最终名单。提供本地文件链接与未完成项，不把流程测试输出当正式招聘结论。候选人资料仅保存在用户指定位置，不随安装包、测试证据或代码发布。

安装与升级按包内 INSTALL.md 操作。Windows 和 macOS 分别验收；不得把 Mac 测试结果写成 Windows 已通过，也不自动更改全局客户端、扩展或通信配置。

## 保存搜索方案的页面前置

猎聘的“保存条件”入口依赖已提交的非关键词筛选摘要。仅关键词或尚未提交的输入草稿可能不显示该入口。保存当前条件前先核对可见摘要和唯一按钮；缺少前置时说明原因，复用用户已批准的筛选需求准备，不能擅自增加筛选、触发搜索、修改CSS或强点隐藏按钮。方案应用可能触发真实查询，计入批准范围；仅清理本轮创建的测试方案，已有方案不动。

## 搜索前集中确认收藏分组

第一次提交搜索前，集中询问：“本次搜索到的人选后续要加入哪些收藏分组？可从已知现有分组中选择，也可选本次不收藏。”已知道现有列表时展示分组名称；尚不知道时先让用户提供目标名称，或只读查询分组，不为列组选读简历。

将用户原话、目标分组名称、确认时间与适用任务范围保存在任务的授权scope及事件记录中。继续同一任务时复用已有选择，不每次搜索或每个人选重复询问；用户改变要求或原组不存在时才重新确认。用户未决定时不能默认选“未分组”。多个目标组时，先明确人选与分组的对应关系，不把同一人选循环添加到多个组。

选择分组只是确定后续目标，不自动授权收藏全部结果，也不触发创建分组。实际收藏仍需已有的人选/数量/动作授权，并在写入前核对页面中的准确分组和回读结果。用户选择“本次不收藏”时正常搜索、读取和报告，跳过收藏写入。

历史分组列表仅供参考，不能据此认定当前分组不存在。收藏时以当前弹层可见分组为准，核对准确名称和选中状态后才保存；当前列表未找到目标时停止，不擅自创建或换组。

## 标准确认、收藏授权与反馈迭代

先把用户给定标准整理为必须、加分、可接受例外和待沟通事项。已确认标准复用，不反复重问。用户授权“按JD综合判断、合适的直接收藏”时，将原话、适用任务、分组及范围写入任务事件与操作授权；这是收藏行为授权，不等于给全部结果批量收藏。

对进入详情核实的人选采用同一套关键条件逐项整理证据，不能只核对其中一个字段就给出整体判断。岗位技能、相关经历和资格作为依据；简历未写视为未知而非不具备。支持事实与推断分列，不能用关键词计数代替综合核实。边界人选可集中请用户校准，不给已经明确授权的每一位人选新增审批。

执行顺序：标准与范围确认→关键词探索→搜索及逐条列表复核→按需要补读详情→统一证据对照→在授权内收藏并核验目标分组→交付结果及边界案例→沿用用户反馈修订后续判断。目标是找到值得跟进的人，报告和采集数量不作为独立完成标准。无充分依据时允许本轮收藏为零，并说明下一轮改进方向。

HTML评估交付默认生成3个同目录文件：重点摘要、`.details.html`已保存详情、`.records.json`原始记录。统计快照放在摘要顶部；桌面表格、手机窄屏纵向展示，不要求用户展开多层内容。姓名下提供本地详情和已观察且身份一致的平台原简历链接，不拼猜URL。平台原链接需要对应登录权限；本地详情只包含已保存可见内容，partial不称完整。交付3个文件链接，移动时一起保留；不把原始JSON嵌回主报告。
